# Агент подбора тем по поисковому спросу (Wordstat)

**Дата:** 2026-10-03
**Статус:** утверждён (брейншторм) — решения по развилкам в разделе «Решения»
**Область:** `backend/internal/wordstat` (новый), `internal/agents`, `internal/orchestrator`, `internal/config`, `internal/httpapi`, `frontend/src`

## Проблема

Темы статей сейчас придумывает `Strategist` — прямо из брифа, без данных о спросе. Темы
получаются правдоподобными, но не подтверждёнными: нет ответа на вопросы «а ищут ли это вообще»,
«сколько людей ищут», «какими словами». Нужны темы, построенные на поисковом спросе, и у каждой —
доказательства: 5–6 реальных запросов с частотностями, объём темы, цель и задача.

Требования заказчика:

- тем — **×2 от нужного количества** (МП предполагает 3 статьи → предлагаем 6 идей);
- каждая тема подкреплена **5–6 примерами запросов** с оценкой совокупной частотности;
- у каждой темы — **цель** (кого и в какой момент ловим) и **задача** (что даём читателю);
- если спроса по продукту нет или он ниже порога — **темы от себя**, но строго по ЦА, продукту
  и задаче из брифа;
- итог оформляется по шаблону заказчика (файл-пример появится позже — см. «Решения»).

## Решение

Новый этап пайплайна — **research**: подбор тем на данных Wordstat **внутри прогона кампании**,
перед написанием статей.

Порядок: **сеялки** (LLM по брифу) → **сбор спроса** (код, Wordstat) → **кластеры-кандидаты**
(LLM группирует уже полученные фразы) → **авто-отбор N из 2N** (код, по объёму) →
**хук, цель, задача** (LLM) → **валидация цитат** (код) → существующий цикл
«копирайтер → критик» по выбранным N темам.

Два принципа, на которых держится вся конструкция:

1. **Числа считает код, LLM только формулирует.** Частотности, объёмы, суммы, сезонность и списки
   запросов берутся из ответов API. Модель не имеет права возвращать цифры — иначе она будет
   уверенно их выдумывать. Этот принцип уже общий для проекта («всё, что можно посчитать, считает
   API»), здесь он критичен.
2. **Каждая цитата проверяема.** Любой запрос, на который ссылается модель, обязан присутствовать
   в полученном наборе — проверяется программно. Не прошло — ретрай, затем ошибка прогона.

**Прозрачность без потери контроля.** В результат кампании попадают **все 2N кандидатов с
доказательствами** (объём, запросы, сезонность, источник), а в генерацию уходят N отобранных.
Пользователь видит, из чего выбирали и почему; сама дорогая часть — research — сохраняется
в результате, поэтому «перегенерировать с другим набором тем» добавляется позже без повторного
обращения к Wordstat.

(Отклонено: чистый LLM-подбор тем без данных — это ровно текущее поведение `Strategist`;
отдельный ресурс `research` со своим экраном выбора — пользователь выбрал авто-отбор, а лишний
ресурс это таблица, миграция и экран; своя кластеризация без LLM — дороже в разработке и хуже
на неочевидных темах; парсинг выдачи Яндекса — против правил и хрупко.)

## Источник данных: контракт проверен живьём

Источник — Wordstat API (Яндекс, Search API v2) **через собственный MCP-сервер**
`yandex-wordstat-mcp-golang`, контракт **1.2.0**, проверен на живом
`dev.coresmart.tech/wordstat-mcp/mcp`.

| Инструмент | Что даёт | Поля результата |
|---|---|---|
| `top_requests` | спрос за 30 дней | `totalCount`, `requests[]`, `associations[]`, `hasData`, `cacheHit`, эхо `regions`/`devices` |
| `dynamics` | сезонность (день/неделя/месяц) | `points[]` с `count` и `share` |
| `regions` | география | `regionId`, `name` (при `includeNames`), `count`, `share`, `affinityIndex`, отсортировано по убыванию |
| `list_regions` | справочник регионов | плоский список с `depth`/`parentId` |

Ошибки типизированы: `invalid_argument` (повтор не поможет), `quota_exceeded` и
`upstream_unavailable` (`retryable = true`), `internal`. Отсутствие спроса — **не ошибка**:
`hasData = false`, `totalCount = 0`.

Плата за выбранный путь: прод-бэкенд зависит от доступности внутреннего MCP-сервиса. Смягчаем
тем, что при исчерпании ретраев прогон падает с внятной ошибкой, а темы не подменяются молча
выдумкой. Свой ключ Яндекса проекту не нужен — он живёт на стороне MCP.

### Что показали замеры (на них опираются правила метрики)

- **Суммировать частотности формулировок нельзя.** «зимняя резина»: `totalCount` 1 028 481,
  а сумма 50 популярных формулировок — 3 487 006, то есть **3.39×**. «аренда офиса»: 48 790
  против 267 456 — **5.48×**. Причина структурная: `requests` — подмножества `totalCount`.
- **Сезонность кратна.** «зимняя резина» по месяцам: окт 1 700 930 → июн 192 109 (размах
  **8.9×**). Порог, посчитанный по окну 30 дней, летом отсечёт живые темы.
- **`requests` — не темы.** В топ-50 «зимней резины» 22 фразы — размеры и техника
  (`зимняя резина 205 55 16`), это 24.4% объёма; вопросных всего 5. У «аренда офиса» вопросных
  в топ-50 нет вообще — темы придётся собирать из других сеялок и из `associations`.
- **`associations` шумят.** Для «аренда офиса» приходят «офисные кресла купить», «офисные линзы»,
  «офисм». Их нельзя отдавать в тему сырыми — только через группировку с валидацией.
- **География решает.** Для «зимней резины» вся Россия — 1 028 481, только Москва — 86 563
  (8%), Москва + телефоны — 72 097. `affinityIndex` показывает, где тема перепредставлена
  (Москва и область — 172).

## Архитектура

### 1. Пакет `internal/wordstat` (новый) — клиент MCP

```go
type Source interface {
    TopRequests(ctx context.Context, p TopParams) (*Top, error)
    Dynamics(ctx context.Context, p DynamicsParams) (*Dynamics, error)
    Regions(ctx context.Context, p RegionsParams) (*Regions, error)
}

type TopParams struct {
    Phrase     string
    NumPhrases int
    Regions    []string // geo ID: "213" Москва, "1" Москва и область, "225" Россия
    Devices    []string
}
```

Реализация одна — `mcp.go`: Streamable HTTP, заголовок `Authorization: Basic ...`, JSON-RPC
(`initialize` → `notifications/initialized` → `tools/call`), из ответа берём `structuredContent`,
а не текст. Ответы приходят в SSE-обёртке (`data: {...}`) — разбираем аккуратно. Сессия
(`Mcp-Session-Id`) переиспользуется на прогон, при обрыве — переподключение.

Ошибки MCP маппятся в sentinel-ошибки (`ErrInvalidArgument`, `ErrQuotaExceeded`/`retryable`,
`ErrUnavailable`, `ErrInternal`) — по образцу того, как это уже сделано в MCP-репозитории,
чтобы раннер мог решать про ретраи, а не разбирать строки.

`fake.go` — для тестов, как `llm.FakeClient` в существующем коде.

**Кэш своего уровня не делаем в фазе 1:** у MCP уже есть внутрипроцессный кэш с TTL 24 часа
и флагом `cacheHit`. Свой кэш в SQLite добавим только если понадобится переживать рестарты
MCP или отдавать данные при его недоступности (фаза 2).

### 2. Агент — `internal/agents/semanticist.go` (новый)

Роль `semanticist` идёт на `MODEL_DEFAULT` (рассуждения важнее скорости). Два обращения к LLM:

```go
// 1) сеялки: 10–15 фраз, которые реально вводят пользователи
Seeds(ctx, brief) ([]string, llm.Usage, error)

// 2) группировка уже полученных фраз в темы-кандидаты
Cluster(ctx, brief, phrases []PhraseCount) ([]TopicDraft, llm.Usage, error)
```

`TopicDraft` от модели: `title`, `goal`, `task`, `queries []string` (только из переданного списка),
`intent`. Объём, суммы, сезонность и `source` дописывает код — модель их не видит и не считает.

Промпт-контракт фиксируем тестами с `llm.FakeClient`, включая негативный кейс: модель сослалась
на запрос, которого нет в наборе → ошибка валидации.

### 3. Типы результата

```go
type TopicCandidate struct {
    ID        string        `json:"id"`
    Title     string        `json:"title"`   // хук: популярная формулировка + утверждение
    Goal      string        `json:"goal"`    // кого и в какой момент ловим
    Task      string        `json:"task"`    // что даём читателю
    Source    string        `json:"source"`  // "wordstat" | "llm"
    Selected  bool          `json:"selected"`// ушла ли тема в генерацию
    Volume    int64         `json:"volume"`  // totalCount головной фразы
    Head      string        `json:"head"`    // головная фраза темы
    Queries   []PhraseCount `json:"queries"` // 5–6 доказательств с частотностями
    Season    *Seasonality  `json:"season,omitempty"`
    Regions   []RegionShare `json:"regions,omitempty"`
    Intent    string        `json:"intent,omitempty"`
}
```

`Volume` — это `totalCount` головной фразы, **не сумма** `Queries`. Если заказчику нужна сумма,
она идёт отдельным полем с подписью «сумма формулировок, с пересечениями» — но не как объём темы.

Кандидаты (все 2N) живут в `Strategy.TopicCandidates`, выбранные N — в существующем
`Strategy.Topics`, который уже потребляют копирайтеры. Стратегия хранится в БД как JSON, поэтому
**миграция не нужна**: добавили поля — старые записи читаются как есть.

### 4. Оркестратор — новый этап внутри прогона

Отдельного ресурса и таблицы нет: research — это первый этап `orchestrator.Run`.

```
Pending → Researching (сеялки → сбор спроса → кластеризация → отбор) → Producing → Done
```

- `Phase` получает значение `researching`; `Snapshot` — те же `TopicProgress`, но на этом этапе
  в них лежат сеялки и их состояние (запрос к Wordstat идёт, готов, ошибка), поэтому фронт видит
  прогресс сбора без изменений в модели.
- В генерацию уходят N тем, отобранных кодом (топ по объёму, с учётом порога и сезонной поправки).
- Если кандидатов меньше 2N или спроса нет — добираем темы от LLM с `source = "llm"`.
- `WORDSTAT_MAX_CALLS_PER_RUN` ограничивает число обращений; при достижении лимита раскрытие
  прекращается, результат помечается неполным.

Ошибки: `hasData = false` — не ошибка (fallback); `quota_exceeded`/`upstream_unavailable` —
ретраи с backoff, при исчерпании прогон `failed` с понятным текстом; `invalid_argument` —
ошибка ввода (регион/фраза) и показывается в форме до запуска.

### 5. Метрика и правила отбора (ядро ценности)

- **Объём темы** = `totalCount` головной фразы за 30 дней.
- **Порог**: абсолютный минимум (`WORDSTAT_MIN_VOLUME`, стартовое значение — 300) **плюс**
  сезонная поправка: если в окне 30 дней тема ниже порога, но её пик за 12 месяцев по `dynamics`
  выше порога в `WORDSTAT_SEASONALITY_FACTOR` раз — тема остаётся и помечается сезонной.
- **Ранжирование** — по объёму, отсечение по минимуму. Пороги не могут быть одними на все ниши:
  для локального бизнеса абсолютные числа маленькие.
- **Интент**: вопросные формулировки (`как`, `какую`, `какая лучше`, `сколько`, `или`) — материал
  для тем; размеры, модели и «купить» — не темы (но годятся как доказательства коммерческого
  интереса). Разделение делает код регулярками + подсказка модели, финальное слово — за моделью
  при группировке.
- **Регион**: из брифа; фильтр применяется в `top_requests`, а `regions`/`affinityIndex` —
  для проверки локализации темы.
- **Fallback** (пункт 4 требований): темы от LLM помечаются `source = "llm"` и **не показывают
  цифры**. Пользователь должен видеть, где данные, а где гипотеза.

### 6. Бриф и конфиг

`agents.Brief` расширяется полями `Region string` (geo ID, дефолт `225` — Россия) и
`TopicsCount int` (из МП; по умолчанию 3, предлагаем 6). Бриф хранится как JSON — миграция
не нужна.

Конфиг (по образцу существующего `config.go`): `WORDSTAT_MCP_URL`,
`WORDSTAT_MCP_USER`, `WORDSTAT_MCP_PASS`, `WORDSTAT_REGION_DEFAULT` (`225`),
`WORDSTAT_MIN_VOLUME`, `WORDSTAT_SEASONALITY_FACTOR`, `WORDSTAT_MAX_CALLS_PER_RUN`,
`TOPICS_MULTIPLIER` (2). Креды MCP — только в `backend/.env` (в git не попадает).

### 7. Фронтенд

- в форме кампании — регион и число статей;
- в результате кампании — блок «Рассмотренные темы»: все 2N кандидатов с объёмом, сезонностью,
  запросами-доказательствами, целью/задачей и бейджем источника; выбранные N помечены и идут
  первыми (генерация — по ним);
- типы `TopicCandidate`/`Seasonality` в `lib/api/types.ts`, подписи в `labels.ts`, тесты vitest
  на новые типы/лейблы, `svelte-check`.

## Тестирование

- `internal/wordstat`: клиент MCP против `httptest`-сервера — JSON-RPC, SSE-обёртка,
  `structuredContent`, переподключение, маппинг ошибок и `retryable`.
- `internal/agents`: промпт-контракт `semanticist` с `llm.FakeClient`, включая негативный кейс
  с чужой цитатой.
- `internal/orchestrator`: прогон на фейковом источнике + фейковом LLM: сеялки, отбор 2N→N,
  пороги, сезонная поправка, fallback без спроса, лимит вызовов.
- `internal/httpapi`: прогон кампании с research-этапом, `researching` в SSE-прогрессе.
- frontend: vitest на новые типы/лейблы + `svelte-check`.
- **Фикстуры** — живые ответы MCP в формате `structuredContent` снимаем в
  `internal/wordstat/testdata`, чтобы тесты не жгли квоты (часть уже снята, её надо переснять
  в новом формате — предыдущие снимки делались до появления `structuredContent`).

## Фазы

- **Фаза 1 (MVP, без UI):** пакет `wordstat` (клиент MCP + fake) → `Semanticist` → этап
  `researching` в прогоне с авто-отбором N из 2N → кандидаты в результате кампании. Тесты
  на фикстурах. Ценность уже здесь: темы с доказательствами вместо фантазий, всё видно в JSON.
- **Фаза 2:** регион и число статей в форме, блок кандидатов в UI, `researching` в лейблах
  прогресса; при необходимости — свой кэш в SQLite и «перегенерировать по другому набору тем»
  (дёшево: research уже сохранён).
- **Фаза 3:** сезонная поправка в отчёте, учёт числа вызовов и стоимости, экспорт по шаблону
  заказчика.

## Вне области (YAGNI)

- кластеризация без LLM, эмбеддинги, ML-ранжирование;
- парсинг выдачи Яндекса и любые обходы API;
- отдельный ресурс `/api/research` и экран выбора тем (решение принято: авто-отбор);
- свой прямой клиент Search API v2 (решение принято: через MCP);
- мультиаккаунтность Wordstat, биллинг квот, автопубликация в CMS.

## Решения по развилкам

1. **Источник в проде — MCP** (не напрямую в Search API). Следствие: свой ключ Яндекса не нужен,
   но появляется зависимость от доступности MCP-сервиса; она покрыта ретраями и явной ошибкой.
2. **Отбор N из 2N — только авто**, без UI-выбора. Следствие: research становится этапом прогона,
   без нового ресурса, таблицы и экрана; все 2N кандидатов сохраняются в результате кампании,
   поэтому интерактивный выбор можно добавить позже без повторного research.
3. **Регион — поле брифа**, дефолт «Россия» (225). Для локальных проектов без него теряется смысл
   фильтра: Москва даёт лишь 8% общероссийского спроса по проверенной фразе.
4. **Шаблон отчёта — позже.** Фазы 1–2 показывают темы с доказательствами в UI/JSON, экспорт
   по шаблону заказчика — фаза 3.
