# Слои по фичам и исправление выявленных проблем

Дата: 2026-10-05. Статус: согласовано пользователем («ок го»); требуется план реализации.

## Цель и согласованный объём

Пользователь предложил пример `core` + `features/<feature>/{repository,service,transport}`
с явной сборкой зависимостей в `main`. Дополнительно выбрал исправление выявленных
проблем. Перенос включает backend и необходимые изменения frontend, SQL-миграций,
конфигурации, документации и проверок. MariaDB/GORM, DeepSeek, Wordstat и SvelteKit
остаются текущими технологиями. Существующие `/api/*` и `/healthz` сохраняются;
версионирование API и смена библиотек в этот объём не входят.

Наблюдения из разговора — кандидаты на исправление, а не подтверждённые тестами
дефекты. Перед каждым изменением проверяется фактическое поведение. Ограничения
продукта исправляются согласно решениям ниже, а не произвольной сменой поведения.
Локальные пустые строки в `backend/cmd/server/main.go` не являются отдельной задачей.

## Целевая структура

```text
backend/internal/
  core/
    config/
    logger/                       # контракт логгера
    llm/                          # Client, Usage, контракты тарификации
    run/                          # Snapshot, Phase, интерфейсы прогресса
    repository/mariadb/pool/
    transport/http/server/
    transport/http/middleware/
  features/
    campaign/
      domain/
      service/                    # use cases, workflow и агенты генерации
      repository/mariadb/
      transport/http/
    review/
      domain/
      service/                    # use cases, workflow и агенты проверки
      repository/mariadb/
      transport/http/
    topic/
      domain/
      service/                    # research и семантический агент
      source/wordstat/
    trace/
      domain/
      service/                    # recorder и чтение трассы
      repository/mariadb/
      transport/http/
  application/runner/             # admission, workers, SSE hub, shutdown
  adapters/llm/deepseek/
  adapters/logger/slog/
  adapters/tracing/               # декораторы LLM и источника спроса
  testkit/                        # моки и временная тестовая БД
backend/cmd/server/main.go         # composition root
```

`score` переезжает в `core/score` как общий чистый набор градаций. `topic` не
получает пустой repository: research сохраняется через workflow кампании.
Общие HTTP DTO ошибок и регистрации маршрутов находятся в core transport.
DOCX parsing относится к review service, а HTTP только принимает загрузку.

## Границы и зависимости

- Domain содержит сущности и чистые правила; не импортирует GORM, HTTP,
  конкретного клиента модели или transport/service.
- Service объявляет необходимые интерфейсы репозитория, исполнителя фоновых
  задач и внешних инструментов; получает реализации через конструктор.
- Repository реализует интерфейс service и преобразует модели БД в domain.
- Transport объявляет узкий интерфейс нужных ему use cases. HTTP handlers
  не вызывают GORM/repository и не управляют выполнением агентов напрямую.
- Campaign service использует topic service через контракт. У topic собственный
  Briefing, чтобы не создавать цикл campaign ↔ topic.
- Core не импортирует features или application. Application runner принимает
  задачи и интерфейсы исполнителей, но не создаёт HTTP handlers или агентов.
- Trace — общая фича: другие сервисы могут зависеть от её контракта Recorder,
  но trace не зависит от campaign/review. Проверка существования прогона для
  trace endpoints передаётся интерфейсом из composition root.
- `main` собирает logger, pool, adapters, repositories, workflows, runner,
  feature services, feature handlers и HTTP server. Сборки графа в init нет.

Сначала выполняется перенос с прежним поведением; исправления идут отдельными
проверяемыми шагами. В финале старые пакеты и временные алиасы удаляются.

## Надёжность выполнения и сохранение

1. Admission выполняется до создания записи; переполнение возвращает HTTP 503
   с кодом `busy`, без зависшего запроса и сиротской pending-записи. Принятый
   слот освобождается и при ошибке Create. Внутренние задачи учитываются отдельно
   от лимита конкурентности; новые задачи не принимаются при shutdown.
2. Shutdown останавливает приём, даёт задачам ограниченное время, затем отменяет
   их и ограниченно ждёт завершения. Запись финального состояния использует
   отдельный короткий timeout, а не бесконечный WithoutCancel.
3. Прогресс получает монотонную revision. Старый снимок не перезаписывает новый
   в БД и не откатывает SSE. Закрытие канала не пересекается с отправкой.
   Ошибки записи видимы в логах; status и терминальный progress согласованы.
4. Ошибки MarkRunning, Complete и Fail проходят единый путь завершения.
   Если БД недоступна, ошибка логируется и позже устраняется recovery;
   нельзя гарантировать сохранение failed при недоступном хранилище.
5. Сохраняются исходные тексты review, результат research, стратегия и каждая
   готовая статья/отчёт. При падении доступны частичные результаты и расходы.
   Повторный запуск отдельного этапа проектируется как явный use case, с
   сохранённым входом и уникальными позициями результатов, без дублей статей.
6. Добавляется Idempotency-Key для создания прогонов. Ключ вместе с хешем
   входа хранится в БД; повтор того же входа возвращает исходный id, иной вход
   с тем же ключом возвращает 409. Ключ не содержит исходный текст. Фронт
   сохраняет ключ для повторной отправки одного и того же неизменённого брифа.
7. Recovery различает владельцев выполнения с помощью lease и heartbeat.
   Старт нового процесса не завершает живую задачу другого процесса.
   Для SSE чужого активного прогона используется чтение progress из БД до
   терминального состояния; такой прогон не объявляется завершённым локальным hub.

## Входы и ответы агентов

- Критик получает полный бриф, тему и стратегию; доработка получает тот же
  исходный контекст, предыдущую статью и замечания.
- Ответы валидируются в service: обязательные поля, непустой текст после trim,
  допустимые verdict и диапазоны score. Отсутствующий score отличим от нуля.
  JSON-декодирование само по себе не означает корректный ответ агента.
- Ноль итераций критика означает генерацию без критики: статья сохраняется,
  review отсутствует явно, UI показывает «не проверено», а не фиктивный 0/100.
- TopicsCount соблюдается с Wordstat и без него. API и UI используют один
  верхний предел из конфига; превышение отклоняется до платного прогона.
  Если research выбрал меньше тем, возвращается явное предупреждение;
  при наличии спроса автоматического добора выдуманных тем нет.
- Отбор входных фраз учитывает coverage по сеялкам и различает requests и
  associations, чтобы глобальный top-40 не вытеснял все узкие запросы. Модель
  сохраняет право выбора, цитаты и частотности по-прежнему проверяет код.
  Проверяется набор фиксированных брифов и сырых ответов Wordstat.
- Лимит HTTP JSON — 2 MiB; не более 20 текстов проверки, каждый до 512 KiB;
  переполнение возвращает понятную ошибку до записи в БД и вызовов модели.
  Лимиты configurable; Node proxy также ограничивает upload до буферизации.
- Лимиты параллельных прогонов и запросов LLM задаются отдельно. Внутри прогона
  обрабатывается ограниченное число текстов одновременно; стартовый предел 4.

## MCP, конфигурация и стоимость

- Потеря MCP-сессии определяется по статусу и структурированной ошибке, а не
  наличию слова session в успешном результате. Сброс не уничтожает более новую
  сессию, уже созданную параллельным вызовом.
- Бюджет Wordstat включает повторные tool calls. Метрики отдельно показывают
  логические вызовы, фактические обращения и служебную инициализацию.
- URI БД строится через url.URL/UserPassword, включая compose migrate и тестовый
  путь: пробелы и специальные символы в credentials проходят round-trip.
- CheckSchema требует все версии миграций, необходимые текущему бинарю,
  а не любую запись schema_migrations. Миграции по-прежнему внешние.
- RATE_LIMIT_PER_MIN=0 явно означает отключённый rate limiter.
- Стоимость — оценка по конфигурируемым ставкам каждой модели, без обращения
  к живым прайс-листам. Usage и стоимость не теряются на ошибках research и review;
  UI обозначает сумму как оценочную. Неизвестная ставка не заменяется нулём молча.

## Трасса

- Summary не сохраняет фрагменты prompt/response ни в payload, ни в error.
  Публичная ошибка и диагностические данные разделены; full сохраняет ответ
  модели и данные Wordstat в пределах лимита.
- Ошибка timeout и итог прогона записываются с отдельным ограниченным контекстом.
  Сбой trace sink не валит платный прогон, но остаётся наблюдаемым.
- Счётчики завершённых прогонов освобождаются. Периодическая retention работает
  во время жизни сервиса. Payload truncation хранится структурированно с
  признаком truncated, а не выдаётся за полный JSON.
- Лента имеет pagination/cursor и честный признак наличия следующих событий.
  Review оставляет итоговое событие так же, как campaign.
- UI обновляет открытую трассу во время выполнения с ограниченным polling,
  прекращает его при завершении/размонтировании и предлагает retry при ошибке.

## UI и чтение результатов

- DOCX загрузки привязаны к стабильному id строки, а не индексу. Удалённая строка
  не получает поздний ответ. Форма ждёт завершения загрузок; повторная загрузка
  не перезаписывается более старым ответом.
- Ошибка XML возвращается пользователю, частичный текст не считается успешным
  извлечением. Лимит извлечённого текста отличён от лимита XML; MIME/ZIP ошибки
  и превышения размера имеют понятные ответы.
- History получает cursor pagination; прежние list endpoints сохраняют форму
  массива, курсор/признак продолжения передаются в заголовках. Поздний ответ
  старого запроса не перезаписывает более свежую историю или карточку.
- Ошибка чтения JSON из БД возвращается как ошибка данных, а не пустой успешный
  результат. Терминальная карточка не отображается как продолжающийся прогон.
- UI показывает research, частичные результаты, предупреждение о меньшем числе
  тем, состояние без критики, reconnect и явные ошибки сохранения/получения.

## Порядок работы и проверка

1. Зафиксировать baseline сборки/типов/тестов и фактические пропуски DB/live тестов.
2. Перенести core/domain/adapters/repositories без изменения поведения.
3. Выделить feature services и transports, собрать граф в main, удалить старые пути.
4. Исправить валидацию, брифы агентов, конфиг и MCP на локальных воспроизведениях.
5. Ввести SQL-миграции для progress revision, partial results, исходных review
   текстов, idempotency и leases; затем исправить runner/recovery/shutdown.
6. Исправить trace и UI, документацию, examples и Makefile.

Критерии: go build/go vet, Go unit tests, тесты репозиториев на настоящей MariaDB,
сквозные сценарии runner → service → repository, race tests для hub/admission/trace,
npm test/check/build. Реальный MCP и платные LLM не нужны для регрессий;
используются httptest и сохранённые фикстуры. DB тесты нельзя считать прошедшими,
если они были пропущены. Для lease, idempotency и порядка снимков проверяются
конкурентные сценарии, не только happy path. Направления импортов проверяются
через go list и анализ внутренних import paths.

## Границы результата

Это существенная миграция, поэтому перенос слоёв и изменения поведения должны
быть отдельно обозримы в diff. Старые записи продолжают читаться; неизвестные
исходные review тексты не восстанавливаются из ничего. Для старых failed-прогонов
без checkpoint повтор отдельного этапа недоступен с понятным объяснением.
Авторизация клиентов, новая версия API и полноценная внешняя очередь задач
не добавляются: они не требуются для согласованного результата.
