# Трасса прогона (Trajectory)

**Дата:** 2026-10-03
**Статус:** утверждён (брейншторм)
**Область:** `internal/trace` (новый), `internal/store`, `internal/llm`, `internal/wordstat`, `internal/orchestrator`, `internal/httpapi`, `internal/config`, `frontend/src`

## Проблема

После прогона видно **состояния и итог**: фазы и темы в `Snapshot`, отобранные темы с
цитатами в `strategy.topic_candidates`, финальное ревью статьи, суммарную стоимость и
счётчик обращений к Wordstat. Не видно **что именно делали агенты**:

- промпты и ответы не хранятся нигде — живой баг с эхом `response_format` мы нашли
  случайно, потому что текст попал в сообщение об ошибке;
- итерации критика выбрасываются: `produce()` оставляет только лучший вариант, а
  промежуточные оценки и замечания исчезают — нельзя ответить «сколько раз переписывали
  и почему»;
- решения отбора тем не видны: есть готовая причина `reject` у кандидата, но нет
  «сеялка → собранные фразы → тема → порог»;
- обращения к Wordstat сведены к числу `wordstat_calls`: неясно, по каким фразам,
  с каким регионом, что вернулось и сколько заняло;
- токены суммируются в один `CostUSD`, хотя модели разнесены по ролям
  (`MODEL_DEFAULT` для стратега и критика, `MODEL_FAST` для копирайтеров);
- латентность неизвестна: непонятно, прогон тормозит из-за Wordstat, стратега или
  цикла критика.

Диагностика сейчас — это догадки по финальному JSON и по одной строке ошибки.

## Решение

**Журнал событий прогона**: append-only таблица `run_events`, куда попадает всё
существенное, с временем, длительностью, токенами и статусом.

Врезка — **декораторы** над уже существующими интерфейсами `llm.Client` и
`wordstat.Source`. Агенты о трассе не знают, их код и поведение не меняются,
отключение — снятие обёртки. Решения (отбор тем, итерации критика, fallback) никаким
декоратором не поймать, поэтому их пишет оркестратор явными вызовами.

Принципы, без которых фича вредна:

1. **Трасса не имеет права сломать прогон.** Ошибки записи логируются и игнорируются;
   никаких возвратов ошибок в пайплайн.
2. **По умолчанию `summary`** — метаданные, решения и метрики, без клиентских текстов.
   Промпты и ответы хранятся только в режиме `full`, который включают осознанно:
   там лежат бриф и черновики статей.
3. **Никаких секретов.** Ключи и заголовки авторизации не пишутся никогда, включая
   режим `full` (запрос Wordstat пишется без заголовков).
4. **Сначала «что делали», потом «что писали».** Первая фаза даёт ответ на главный
   вопрос без хранения текстов; полные тела — вторая.

## Модель данных

Миграция `0002_run_events.sql`:

```sql
CREATE TABLE IF NOT EXISTS run_events (
    id         TEXT PRIMARY KEY,
    run_kind   TEXT NOT NULL,       -- campaign | review
    run_id     TEXT NOT NULL,
    seq        INTEGER NOT NULL,    -- порядковый номер внутри прогона
    at         DATETIME NOT NULL,   -- формат, который драйвер разбирает в time.Time
    kind       TEXT NOT NULL,       -- llm | wordstat | decision | phase | result
    name       TEXT NOT NULL,       -- роль, инструмент или решение
    status     TEXT NOT NULL,       -- ok | error
    duration_ms INTEGER NOT NULL DEFAULT 0,
    prompt_tokens     INTEGER NOT NULL DEFAULT 0,
    completion_tokens INTEGER NOT NULL DEFAULT 0,
    summary    TEXT NOT NULL,       -- человекочитаемая строка для ленты
    payload    TEXT,                -- JSON деталей (в full — промпт и ответ)
    error      TEXT
);
CREATE INDEX IF NOT EXISTS idx_run_events_run ON run_events (run_id, seq);
CREATE INDEX IF NOT EXISTS idx_run_events_at  ON run_events (at);
```

Связи через внешний ключ нет намеренно: события переживают удаление прогона и не
блокируют его, а ретенция чистит их пачками по `at`.

## Архитектура

### 1. `internal/trace` (новый) — типы и рекордер

```go
type Kind string // llm | wordstat | decision | phase | result

type Event struct {
    Kind, Name, Status, Summary string
    DurationMS                  int64
    PromptTokens, CompletionTokens int
    Payload                     any    // сериализуется в JSON; nil в режиме summary
    Error                       string
}

// Sink — хранилище событий (реализует store.SQLite).
type Sink interface { SaveRunEvent(ctx context.Context, runID string, ev Event) error }

type Recorder interface {
    // Event записывает событие прогона; ошибки не возвращаются наружу.
    Event(ctx context.Context, runID string, ev Event)
    // Enabled сообщает, пишем ли мы трассу (режим off).
    Enabled() bool
}
```

Реализации: `Nop` (режим off, тесты), `Recorder` поверх `Sink` с монотонным `seq` на
прогон и обрезкой payload по лимиту. Пишем синхронно: событий на прогон десятки, а не
тысячи, а синхронная запись переживает падение процесса — ради этого трасса и нужна.
Стоимость записи (единицы миллисекунд на SQLite) много меньше времени LLM-вызова.

### 2. `internal/store` — SQL

`SaveRunEvent`, `RunEvents(runID, limit)` (лента без payload), `RunEvent(runID, seq)`
(полное событие), `DeleteRunEventsBefore(cutoff)` (ретенция). SQL остаётся в сторе, как
и весь остальной.

### 3. Декораторы

- `llm.TracingClient{inner, rec}` — роль, модель, токены, длительность, статус,
  ошибка; в режиме `full` — промпт и ответ (обрезанные).
- `wordstat.TracingSource{inner, rec}` — инструмент, фраза, регион, `numPhrases`,
  ответ (`totalCount`, `hasData`, `cacheHit`, число фраз), длительность, ошибка.

Ставятся в `main.go` при сборке клиентов — это единственное место связывания.

### 4. Оркестратор — решения и итерации

События, которых нет в декораторах:

- сеялки: список и количество;
- по каждой сеялке — сколько фраз собрано (и было ли `hasData`);
- кластеризация: сколько тем предложила модель;
- по каждому кандидату — решение: объём, порог, сезонный множитель, `selected`;
- fallback: почему понадобился и сколько тем добавил;
- по каждой итерации критика — номер, `score`, `verdict`, число замечаний;
- итог: токены **по ролям**, число обращений к Wordstat, стоимость.

Токены по ролям считает `TracingClient` (он видит роль в каждом вызове) и отдаёт
сводку через рекордер.

### 5. API

- `GET /api/campaigns/{id}/trajectory` → `{id, kind, total, events: [{seq, at, kind,
  name, status, duration_ms, prompt_tokens, completion_tokens, summary, has_payload}]}`
- `GET /api/campaigns/{id}/trajectory/{seq}` → полное событие вместе с `payload`
- те же два эндпоинта для проверок текстов: `/api/reviews/{id}/trajectory[/{seq}]`

Лента отдаётся без тел (иначе мегабайты на прогон), тела — отдельным запросом.

### 6. Конфиг

- `TRACE_MODE` — `off | summary | full` (по умолчанию `summary`);
- `TRACE_RETENTION_DAYS` — срок хранения событий (по умолчанию 30 дней);
- `TRACE_MAX_PAYLOAD_BYTES` — обрезка одного payload (по умолчанию 32768).

Ретенция выполняется при старте сервиса (как `RecoverInterrupted`), ошибка чистки не
мешает запуску.

### 7. Фронтенд

На странице кампании — раскрывающийся блок «Трасса прогона»: лента шагов с иконкой
вида события, ролью, длительностью, токенами и кратким описанием; шаг раскрывается в
детали (в режиме `full` — промпт и ответ). Типы — в `lib/api/types.ts`, подписи видов
событий — в `labels.ts`, тесты vitest.

## Обработка ошибок и краевые случаи

- запись события не влияет на прогон: ошибка логируется, пайплайн продолжается;
- прогон без событий (старые кампании, режим `off`) → пустая лента, а не 404;
- `payload` отсутствует в `summary` → `has_payload: false`, детальный эндпоинт отдаёт
  событие без тела;
- параллельные темы: `seq` монотонный, лента сортируется по `seq` (порядок
  детерминирован, хотя события пишутся из разных горутин);
- payload обрезается по лимиту с явной пометкой в конце строки;
- ретенция чистит события, но не сами прогоны: кампания и её результат остаются.

## Тестирование

- `internal/trace`: режимы (`off` ничего не пишет, `summary` не пишет payload),
  монотонный `seq`, обрезка payload, ошибка sink не ломает запись;
- `internal/store`: миграция, сохранение и чтение ленты, полное событие по `seq`,
  ретенция по `at`;
- декораторы: `llm` (роль, модель, токены, длительность, статус, состав payload в
  разных режимах), `wordstat` (параметры запроса и результат в payload);
- `orchestrator`: в прогоне появляются события решений и по одной записи на итерацию
  критика, а также сводка по ролям;
- `httpapi`: лента, деталь, 404 для чужого `seq`, пустая трасса;
- frontend: типы и лейблы, тесты vitest.

## Фазы

1. **Бэкенд (эта):** миграция, пакет `trace`, декораторы, решения оркестратора, API,
   конфиг, ретенция, тесты. По умолчанию `summary` — польза есть, клиентских текстов
   в БД нет.
2. **Вьюер:** блок трассы на странице кампании и проверки, живые события в SSE.
3. **Полные трейсы:** `TRACE_MODE=full` как рабочий режим отладки, реплей-фикстуры для
   тестов промптов и метрики качества (доля выдуманных цитат, прирост score за итерацию).

## Вне области (YAGNI)

- распределённый трейсинг и экспорт в OpenTelemetry или внешние системы;
- полнотекстовый поиск по трассе и аналитика по всем прогонам;
- хранение изображений и файлов;
- отдельный UI для сравнения прогонов.
